## 2. CLIENT_URL — почему это критично

`backend/src/reminders.js` строит ссылки для писем так:
```js
`${process.env.CLIENT_URL || "http://localhost:5173"}/verify-email?token=…`
```

Если `CLIENT_URL` не задан или задан с ошибкой:
- письмо подтверждения email ведёт на `localhost` → владелец не может верифицировать аккаунт → салон не виден в поиске;
- (после `feature/ux-improvements`) письма клиенту со ссылкой «Zarządzaj wizytą / перенести / отменить» ведут в никуда.

**Проверка:** зарегистрировать тестовый аккаунт → прийти письму → ссылка должна открывать боевой домен.

## 3. Одноразовый SQL после первого деплоя (Neon → SQL Editor)

Выдать права администратора (доступ к `/admin`):
```sql
UPDATE owners SET role = 'admin' WHERE email = 'borshenkoadam15@gmail.com';
```
Заменить email на нужный, если аккаунт другой. Проверить:
```sql
SELECT email, role FROM owners WHERE role = 'admin';
```

Больше никаких ручных SQL не требуется.

## 4. Email (Resend)

- Аккаунт: resend.com. Ключ → `RESEND_API_KEY` на Render.
- Пока **нет своего домена**: `FROM_EMAIL = Rezerwo <onboarding@resend.dev>` — работает, но письма могут падать в спам и есть лимиты.
- Свой домен (когда будет): Resend → Domains → добавить домен → прописать DNS-записи (SPF/DKIM) у регистратора → дождаться verified → поменять `FROM_EMAIL`.
- Инициализация ленивая: если ключа нет — приложение не падает, просто не шлёт письма (в логах Render будет предупреждение).

**Проверка:** через кабинет отправить себе тестовое (регистрация/бронь) и убедиться, что письмо дошло.

## 6. Миграции БД — почему руками ничего не нужно

Вся схема и все изменения колонок живут в `backend/src/db.js` → `initDb()`, которая вызывается
при каждом `npm start` (то есть при каждом деплое на Render). Формат:
```sql
CREATE TABLE IF NOT EXISTS …
ALTER TABLE … ADD COLUMN IF NOT EXISTS …
CREATE INDEX IF NOT EXISTS …
```
Идемпотентно: повторный запуск безопасен, существующие данные не трогаются.

### Что добавит ветка `feature/ux-improvements` (справочно, действий не требует)

| Таблица | Колонка / объект | Зачем |
|---|---|---|
| `appointments` | `manage_token TEXT` | magic-ссылка клиента для отмены/переноса записи без аккаунта |
| `reviews` | `owner_reply TEXT`, `owner_reply_at TIMESTAMPTZ` | ответы владельца на отзывы |
| `reviews` | (использование существующей `appointment_id`) | «проверенный отзыв» — оставлен после реального визита |
| `review_requests_sent` | новая таблица `(appointment_id UNIQUE, sent_at)` | защита от повторной отправки письма «оставьте отзыв» |

Все — через `ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS`. После мёржа и деплоя
применятся автоматически. **Откат:** колонки не удаляются кодом; при необходимости — вручную в Neon.
